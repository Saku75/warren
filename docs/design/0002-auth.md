# 0002 — Auth & access

Status: **accepted** · 2026-06-12

Phase 2 design: how Warren authenticates people and machines. Goals:
local accounts, LDAP, and OIDC SSO behind one provider model; stateless
replicas (sessions in Postgres); the API as a peer of the UI; secure by
default.

## 1. Model

```
users        one row per person, regardless of how they authenticate
sessions     browser logins (cookie ↔ hashed token), DB-backed
api_tokens   machine credentials for the REST API, per user, hashed
```

- **users**: `id` (UUIDv7), `username` (unique, lowercase,
  `[a-z0-9][a-z0-9._-]*`), `display_name`, `email`, `provider`
  (`local` | `ldap` | `oidc`), `external_id` (subject/DN for external
  providers), `password_hash` (argon2id, local users only), `is_admin`,
  `disabled`, timestamps, `last_login_at`. A user row always exists —
  external providers JIT-create one on first login — so permissions,
  tokens, and the changelog always reference a stable local identity.
- **sessions**: `token_hash` (SHA-256 of a 256-bit random cookie value),
  `csrf_token`, `user_id`, `expires_at` (sliding 7 days, extended on
  use), `ip`, `user_agent`. Cookie: `warren_session`, HttpOnly,
  SameSite=Lax, Secure per `WARREN_COOKIE_SECURE`. Logout deletes the
  row; disabling a user invalidates all their sessions and tokens.
- **api_tokens**: `token_hash`, `name`, optional `expires_at`,
  `last_used_at`. Plaintext shown exactly once at creation, format
  `wrt_<base64url>` (greppable prefix). No scopes yet; tokens act as the
  user (RBAC lands in Phase 7).

Plaintext credentials are never stored: passwords are argon2id
(64 MiB, t=1, p=4 — RFC 9106 low-memory profile), session and API
tokens are stored as SHA-256 digests and compared in constant time.

## 2. Providers

```go
// password-style providers (local, ldap)
type PasswordAuthenticator interface {
    Name() string
    Authenticate(ctx, username, password) (Identity, error)
}
```

Login flow for username+password: look up the user; if found, its
`provider` decides which authenticator verifies the password. If not
found and LDAP is enabled, LDAP is tried and a user row is JIT-created
on success. OIDC is not password-style: `/login/oidc` redirects to the
IdP, the callback verifies the ID token (state + nonce cookies), then
JIT-creates/updates the user by issuer subject and opens a session.

- **local**: argon2id verify against `password_hash`.
- **ldap**: service-account search → user bind (search-then-bind);
  attribute mapping for username/display name/email; optional
  memberOf→admin mapping. Config via `WARREN_LDAP_*`.
- **oidc**: code flow with PKCE via `coreos/go-oidc`; lazy issuer
  discovery (the server boots and serves local logins while the IdP is
  down); claim mapping; optional groups-claim→admin. Config via
  `WARREN_OIDC_*`. Per-attempt state/nonce/PKCE live in short-lived
  HttpOnly cookies scoped to the callback path.

Providers only authenticate; sessions, users, and authorization are
Warren's own and identical across providers.

## 3. Enforcement

Secure by default: every route requires authentication except `/login`,
`/assets/*`, `/healthz`, `/readyz`.

- **UI**: session cookie → user in request context; otherwise 303 to
  `/login?next=<path>` (relative paths only). Mutating UI requests
  (POST/PATCH/DELETE) require the session's CSRF token — hidden input in
  forms, `X-CSRF-Token` header for htmx (set globally via `hx-headers`
  on `<body>`). The login form itself uses a double-submit cookie.
- **API**: `Authorization: Bearer wrt_…` only. Cookies are deliberately
  not accepted on `/api/*`, which keeps the API CSRF-immune.
- **Admin**: user management requires `is_admin`. Everything else is
  any-authenticated-user until RBAC (Phase 7).
- **Actor attribution**: the change log records the authenticated
  username (was: `system`, which remains for CLI/migrations).

## 4. Bootstrap & operations

- `warren user create --username <u> [--name …] [--email …] [--admin]`
  creates a local user; the password is read from stdin (pipe-friendly)
  — no credentials in argv or env. First boot: run it once, then log in.
- Sessions and tokens live in Postgres: any replica can serve any
  request, rolling deploys keep everyone logged in (HA doc §6 holds).
- Expired sessions are deleted opportunistically on validation; a
  periodic sweep can join the Phase 7 job runner.

## 5. Out of scope (this phase)

Password reset flows, MFA/WebAuthn, per-token scopes, fine-grained
RBAC, SCIM provisioning, audit of read access.
